# Sprint planning

Two parts. Part A runs the planning meeting and writes the result to the tracker. Part B reads the running sprint without changing anything.

## Part A: the planning layer

### What the layer does

For each feature in the backlog document, a panel lists its stories with owner, points and target sprint. The meeting fills it in, a review screen shows exactly what will change, and only then are values written to the tracker.

### Rules

1. Dry run first. Show the whole plan before touching anything. Then write.
2. One item first. Publish one card, check it in the tracker, then the batch. A batch generated by AI never goes straight to the board.
3. Points go on stories only, in whichever field your tracker uses for them. Features carry effort, not points. Check your tracker's fields once and write them down.
4. Zero is a value. If the plan has 0 points on an item that already has points, the review screen says "this clears N points on the board" before any write.
5. The owner chosen in the header is the default for the rows, not a write by itself.
6. The per-person limit is a reference, not a measurement. A starting rule is one point per working day of the sprint minus ceremonies. Replace it with measured velocity as soon as the team has it. A few closed sprints is too short a base to become a ceiling.
7. The token that authorizes writes lives in the memory of the open tab and disappears when it closes. Never store it where other local files can read it.
8. Browser-side writes need the tracker's CORS policy to allow the method and the authorization header. Send requests without cookies.
9. Text the tracker returns can be escaped (`&`, quotes, angle brackets). Unescape both sides before comparing, or the check reports false differences.
10. Some tracker forms do not show acceptance criteria on epics and features. The API may accept the write and nobody sees it. At those levels, put the criteria in the description.

### Pitfalls to test for

- A class that sets `display` beats the `hidden` attribute. A modal styled `display:flex` stays visible when hidden. Test open and close.
- Two documents with the same storage key overwrite each other's plan when opened from local files, because they share an origin. Give each its own key.
- After any bulk text replacement, count every proper name in the old and new document. A name that dropped to zero is suspect. Use word boundaries for short terms.

### Process

1. Load the backlog and the team calendar (members, sprint dates).
2. Run the planning meeting in the document: owner, points, sprint per story.
3. Review screen: list every change with old and new value.
4. Dry run. Then write one item. Then the batch.
5. Re-read from the tracker and compare.

## Part B: reading the running sprint

Read only. Nothing here creates, moves or closes a work item.

### Translate states

| In the tracker | In the report |
|---|---|
| Epic | stream (large goal, several cycles) |
| Feature | set of deliverables |
| User story | deliverable, the unit that counts as progress |
| Task | technical task, detail inside a deliverable |
| Sprint | cycle |
| New, Active, Resolved, Closed | not started, in execution, in validation, done |

Done means the team closed it. It does not mean the business accepted it.

Count deliverables, not tasks, or the same stream is counted twice. Exception: a cycle built only from tasks counts tasks, and the report says that the parent story is outside the cycle.

### Attention points come from rules

Each point is a fact plus what to do with it. Examples of rules: two cycles open at once, a cycle with no items, an open item with no owner, in execution with no movement for more than 5 days, a deliverable in execution with no technical task, no estimates, load concentrated on one person when 3 or more people are in the cycle, a deliverable not started halfway through the cycle. Never write a judgment about a person. Write what to bring to the daily.

### PM reading (curated)

3 to 4 bullets per team, in the PM's register:
1. Only what the numbers support. A bullet without a fact behind it does not enter.
2. Say what the scoreboard hides. 17 of 31 done looks like 55%, but if the 17 closed on one day, the real cycle is the 14 still open.
3. A question for the daily, not an accusation.
4. Name the stream that gives scale. If the shared standard is stalled, the next agent is built by hand. Say the consequence.
5. Stamp the date and review at each planning.

## Definition of done

- Every write was previewed and then verified by re-reading the tracker.
- No estimate was cleared without the warning.
- Attention points follow the fact-plus-action form.
- Part B changed nothing in the tracker.
