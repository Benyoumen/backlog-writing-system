# Sprint planning

> Two parts. Part A runs the planning meeting inside the backlog document and writes the result to the tracker. Part B reads the running sprint without changing anything.

## When to use

- Planning the next sprint: owner, points and sprint per story.
- Estimating a batch of stories with the developers.
- Checking how the current sprint is going, in language a manager can read.

## Inputs

- The backlog document and the team calendar (members, sprint dates).
- The tracker's field names for points, effort and iteration, checked once and written down.
- The Definition of Ready (`backlog-standard`): an AI item needs eval cases; an item a coding agent will build needs an agent brief.
- Measured velocity, when the team has it.
- The capacity plan from `capacity-simulation`: owner, week and landing date per story, the reserve for enabling work. This skill writes that plan to the tracker; it does not derive it.

## Procedure

### Part A: the planning layer

1. Load the backlog and the team calendar.
2. Check readiness. A story that is not Ready does not enter the sprint. For an AI item, that means eval cases with a golden set, a scoring method and a threshold exist. For a story a coding agent will build, an agent brief exists.
3. Run the planning meeting in the document: for each Feature, a panel lists its stories with owner, points and target sprint. The meeting fills it in.
4. Show the review screen: every change with old and new value. If the plan puts 0 points on an item that already has points, the screen says "this clears N points on the board" before any write.
5. Dry run. Then write one item. Open it in the tracker and check it. Then write the batch.
6. Re-read from the tracker and compare.

### Part B: reading the running sprint

Read only. Nothing here creates, moves or closes a work item.

1. Translate states for the report:

| In the tracker | In the report |
|---|---|
| Epic | stream (large goal, several cycles) |
| Feature | set of deliverables |
| User Story | deliverable, the unit that counts as progress |
| Task | technical task, detail inside a deliverable |
| Sprint | cycle |
| New, Active, Resolved, Closed | not started, in execution, in validation, done |

Done means the team closed it. It does not mean the business accepted it.

2. Count deliverables, not tasks, or the same stream is counted twice. Exception: a cycle built only from tasks counts tasks, and the report says that the parent story is outside the cycle.
3. Derive attention points from rules. Each point is a fact plus what to do with it. Rules: two cycles open at once; a cycle with no items; an open item with no owner; in execution with no movement for more than 5 days; a deliverable in execution with no technical task; no estimates; load concentrated on one person when 3 or more people are in the cycle; a deliverable not started halfway through the cycle. Never write a judgment about a person. Write what to bring to the daily.
4. Write the PM reading: 3 to 4 bullets per team, in the PM's register. Only what the numbers support; a bullet without a fact behind it does not enter. Say what the scoreboard hides: 17 of 31 done looks like 55 percent, but if the 17 closed on one day, the real cycle is the 14 still open. A question for the daily, not an accusation. Name the stream that gives scale and say the consequence if it stalls. Stamp the date and review at each planning.

## Rules

1. Dry run first. Show the whole plan before touching anything. Then write.
2. One item first. Publish one card, check it in the tracker, then the batch. A batch generated by AI never goes straight to the board.
3. Points go on stories only, in whichever field your tracker uses for them. Features carry effort, not points.
4. Zero is a value. Clearing points is announced before it happens.
5. The owner chosen in the header is the default for the rows, not a write by itself.
6. The per-person limit is a reference, not a measurement. A starting rule is one point per working day of the sprint minus ceremonies. Replace it with measured velocity as soon as the team has it. A few closed sprints is too short a base to become a ceiling.
7. The token that authorizes writes lives in the memory of the open tab and disappears when it closes. Never store it where other local files can read it.
8. Browser-side writes need the tracker's CORS policy to allow the method and the authorization header. Send requests without cookies.
9. Text the tracker returns can be escaped (`&`, quotes, angle brackets). Unescape both sides before comparing, or the check reports false differences.
10. Some tracker forms do not show acceptance criteria on Epics and Features. The API may accept the write and nobody sees it. At those levels, put the criteria in the description.
11. A reserve of each sprint, a third to start, goes to Enabler and platform stories and is allocated first, so the foundation never waits for the product to finish. A Feature never splits across two sprints. The allocation comes from `capacity-simulation`; this skill writes it after the dry run.

Pitfalls to test for in the planning document: a class that sets `display` beats the `hidden` attribute, so a modal styled `display:flex` stays visible when hidden; two documents with the same storage key overwrite each other's plan when opened from local files, so give each its own key; after any bulk text replacement, count every proper name in the old and new document, and treat a name that dropped to zero as suspect.

## Checklist

- [ ] Every story entering the sprint is Ready; AI items have eval cases, agent-built items have a brief.
- [ ] Review screen shown with old and new values before any write.
- [ ] Any cleared estimate was announced.
- [ ] Dry run, then one item checked in the tracker, then the batch.
- [ ] Re-read from the tracker and compared.
- [ ] Part B changed nothing in the tracker.
- [ ] Attention points follow the fact-plus-action form; no judgment about a person.
- [ ] PM reading is 3 to 4 bullets, each backed by a number, date stamped.

## Example

Weak attention point: "The CRM stream is behind because the developer on it is slow."

Corrected: "Stream CRM write-back: 2 of 5 deliverables done at day 7 of 10, one in execution with no movement for 6 days (ACME-E01-F03-US03). Bring to the daily: is the field mapping blocking it, and does the owner need a second person for two days?" (Illustrative.)

## Definition of done

Every write was previewed and then verified by re-reading the tracker; no estimate was cleared without the warning; no story entered the sprint without being Ready; attention points follow the fact-plus-action form; Part B changed nothing in the tracker.
